## 1. Mainline `-sm tensor` internals (Nov 2026)

Model (docs/multi-gpu.md): `tensor` = "EXPERIMENTAL. Tensor parallelism that splits both weights *and* KV across the participating GPUs via a 'meta device' abstraction." Hard requirements: flash-attn on; KV cache f32/f16/bf16 only (quantized KV "not implemented"); `-fit` not supported. Current deny list: MoE/hybrid Grok, MPT, OLMoE, DeepSeek2, GLM-DSA, Nemotron-H(-MoE), Granite-Hybrid, LFM2-MoE, Minimax-M2, Mistral4, Kimi-Linear, Jamba, Falcon-H1; Mamba/Mamba2; PLAMO2, MiniCPM3, Gemma-3n, OLMo2, BitNet, T5. **qwen35moe (Qwen3.6-35B-A3B) is NOT denied** — allowed. (Recent movement: #28569 "re-enable -sm tensor for qwen4exp"; #31081, merged 2026-10-24, added `mellum`/`flint` to the deny for MoE amax rescaling under split axis 0; #30798 still requests nemotron_h_moe.)

Inter-GPU communication:
- NCCL is build-time only (multi-gpu.md): "There's no runtime flag for NCCL - it's selected at build time (`-DGGML_CUDA_NCCL=ON`, this is the default)... When llama.cpp is compiled with NCCL support it uses it automatically for cross-GPU reductions in `tensor` mode." Missing NCCL prints once: "NVIDIA Collective Communications Library (NCCL) is unavailable, multi GPU performance will be suboptimal".
- Fallback without NCCL, 2 GPUs: internal AllReduce in ggml/src/ggml-cuda/allreduce.cu (verbatim): "Used by the tensor-split path alongside NCCL; targets setups without NVLink/xGMI, where data is exchanged between the GPUs by staging it through pinned host memory over PCIe." Two paths: (a) chunked kernel (<=1 MiB): one kernel stages through pinned host + local sum, cross-GPU sync *inside* the kernel (busy-wait on a host-memory flag); (b) copy-engine path (>=1 MiB): D2H+H2D cudaMemcpyAsync chunks + device-side add kernel, event sync. No P2P used here: "atomicAdd_system() requires hostNativeAtomicSupported, which is unavailable on PCIe-attached consumer GPUs without NVLink, so the volatile path is the portable choice."
- **Pre-Volta gate — the Maxwell-relevant finding** (`ggml_cuda_ar_pipeline_init`): `n_devices != 2` -> "internal AllReduce only supports n_devices=2 (got %zu); falling back"; and `if (cc < GGML_CUDA_CC_VOLTA)` -> "internal AllReduce requires compute capability >= %d (device %d has cc=%d); falling back" (kernel uses `__nanosleep`, sm70+). So on Maxwell sm_50 (and Pascal sm_60/61) the internal AR is unavailable, and for >2 GPUs it is unavailable regardless. Per the file's MUSA comment: "The dispatcher in ggml-cuda.cu treats a nullptr pipeline as 'init failed' and silently falls back to the meta backend's generic AllReduce." -> 4x GM107 (4 GPUs) + Maxwell lands on that generic path; its implementation not read [UNVERIFIED details].
- P2P: `GGML_CUDA_P2P` is runtime opt-in ("set the environment variable `GGML_CUDA_P2P` to any value to enable it"). Presence-based: "the presence-based semantics of GGML_CUDA_P2P (set = on, even with value 0) are preserved" (#30327, merged 2026-10-13). History: #19378 enabled peer access "guarded only by `cudaDeviceCanAccessPeer`"; #21910 (merged 2026-04-15) made it opt-in: "for some motherboards and BIOS settings this seems to cause crashes or corrupted outputs. I don't think we can feasibly check for this so our only option is to make peer access an explicit opt-in." Docs: "P2P requires driver support (usually restricted to workstation/datacenter GPUs) and may cause crashes or corrupted outputs on some motherboards or BIOS configurations (e.g. when IOMMU is enabled)."
- Tuning env vars (allreduce.cu): `GGML_CUDA_AR_COPY_THRESHOLD` (default 1 MiB), `GGML_CUDA_AR_COPY_CHUNK_BYTES` (default heuristic clamp(nbytes/4, 512 KiB, 2 MiB); floor 256 KiB), `GGML_CUDA_AR_BF16_THRESHOLD` (default 1: BF16 round-trip always on for F32 inputs, "Matches NCCL's behaviour"; =0 disables).
- NCCL multi-node: #28967 (merged 2026-11-03, "Add nccl support for multi-node tensor parallelism", on top of #26610 "RPC: add -sm tensor"): cross-process collectives backend, NCCL implementation "used in the RPC server when available". 27B Q4_K_M, 2x DGX Spark: single-node pp512 846.54 / tg128 13.02; NCCL 1348.29 (1.59x) / 23.51 (1.81x); built-in pairwise 961.61 (1.14x) / 22.33 (1.72x).
- Known issues: #27428 (open) draft-mtp "roughly halves prompt processing on multi-GPU layer split"; #29466 (open) -sm tensor GGML_ASSERT crash 2nd request, 2x/3x P100; #30075 (open) tensor split output degenerates after 2-3 requests (2x P100, meta); #24549 graph reuse disabled when contexts share memory under SPLIT_MODE_TENSOR; speculative.md: "Tensor split mode does not support backend sampling."

## 2. M10 intra-card P2P (PEX8747)

Primary source: crgregersen/m10dis docs/TRANSPORT.md, ARCHITECTURE.md, RESULTS.md.
- Topology: "All GPUs sit below one PEX8748" (outer); "The PEX8747 on every M10 card implements the PCIe Multicast capability (an optional part of the PCIe spec)"; the card's 4 GPU ports are configured as receivers: "A posted write into that window is replicated by the switch to all four GPUs. Only posted writes multicast. Reads and completions don't."
- ACS: "PCIe ACS (Access Control Services) on the switch's downstream ports would normally redirect peer requests up to the CPU's root port. The runner clears only the request and completion redirect bits (PCI_ACS_RR | PCI_ACS_CR) on the seven PEX8748 ports of the M10 cards and the RTX, and on the 20 PEX8747 GPU ports of the five routed cards (for the card sums). It saves every original value and restores it afterwards." -> intra-card P2P flows at PCIe level through the PEX8747's ports with ACS redirect cleared.
- CUDA peer access: "CUDA offers no peer access between the RTX and the M10s, so an RTX kernel can't simply store into M10 memory." m10dis patches nvidia-uvm (transport/driver/patches/, e.g. 580.178.04-qwen38-rtx-peer-multiroute.patch) to "rewrite a GPU page-table entry so that a normal device virtual address points at a chosen physical PCIe address." The SAME PTE-remap mechanism serves the intra-card sums (PTE table: "Card sum (M10 -> M10) | each peer | the card leader's BAR1"). -> No public cudaDeviceCanAccessPeer output for M10 found; the use of remapped PTEs for GM107->GM107 implies native CUDA P2P is unavailable even within one card [UNVERIFIED as a literal API result].
- nvidia-smi topo -m: no public example found for M10 (two web searches empty; not in m10dis docs). Expected shape: 4 GM107 PCI devices per card under one bridge behind the PEX8747 [inference from spec].
- Measured (no GB/s P2P bandwidth published anywhere found): peer push "push + fence + flag ~ 11 us" for one 2560-float (10 KiB) row; multi-row verify exchange "150 / 239 / 337 / 432 us per layer for 1 / 2 / 3 / 4 rows (bandwidth-bound)"; the RTX's Gen3 x4 link is the limit from 2 rows on: "13.8 MB per 64-row call through the RTX's Gen3 x4 link, 0.83x (t6)" — on-card leader sums beat returning everything to the RTX. Link ceilings (spec, not measured): ~15.75 GB/s per Gen3 x8 GM107 port, ~3.9 GB/s x4 card uplink. ARCHITECTURE.md: the GM107s "never talk to each other except within a card."

## 3. MTP speculative decoding, Qwen3.6-35B-A3B

- Support: #22673 (am17an; "I tested this on Qwen3.6 27B and Qwen3.6 35BA3B"); official GGUFs ggml-org/Qwen3.6-35B-A3B-MTP-GGUF (+ am17an/Qwen3.6-35BA3B-MTP-GGUF). "MTP is compatible with Vision input and Tensor/Pipeline Parallelism."
- Published acceptance (27B dense Q8_0, DGX Spark, #22673): baseline 7.0-7.3 t/s; n-max 3: aggregate 0.7218, 15.8-21.6 t/s (code_python rate 0.908/21.6; translation 0.542/13.9), wall 83.8 s; n-max 2: 0.8258, 15.2-18.2 t/s, wall 90.44 s. Author: "typically I see a steady-state acceptance of around 75% with 3 draft tokens, which is more than >2x speed-up over baseline." No separate 35B-A3B table published [none found].
- Flags: `--spec-type draft-mtp --spec-draft-n-max 2` ("MTP with draft size N (values for N: 2,3,...)"). `--spec-draft-p-min P`: "truncates each drafted block at the first position whose predicted acceptance (from the draft's confidence head) falls below P (default 0 = disabled)" (speculative.md). MTP p-min: #22673 TODO "Re-enable --spec-draft-p-min support for mtp" checked; no published optimal p-min for MTP [none found]. Experimental: "combine MTP + ngram-* (experimental, suitable for non-CUDA systems)".
- Slow-GPU data — m10dis (24x GM107 + RTX 3070 Ti, Qwen3.8-Flash-Next FP8, vLLM method=mtp, 32,768 ctx): per-position acceptance / t/s: 1 draft 70% (69.8) / 89% (74.1); 2: 70/46% (69.0) / 97/93% (88.3); 3: 67/45/26% (64.3) / 97/96/92% (96.3); tokens/step 1.70/2.16/2.38 (natural), 1.89/2.90/3.84 (humaneval). Verdict: "Suggested: 2 draft tokens by default (1 % behind 1 draft on natural text, 19 % ahead on code), 3 for code-heavy work." And: "The best draft length is lower than on a single GPU, because every verify row costs M10 time: one multi-row exchange takes 150 / 239 / 337 / 432 us per layer for 1 / 2 / 3 / 4 rows." KV cost: pool 84,440 -> 66,628 / 58,789 / 52,601 tokens at 1/2/3 drafts.
- PP caveats: #22673 "Prompt processing (PP) speed typically takes a negative hit when MTP is enabled mainly due to Device-To-Host (D2H) embedding transfers"; #27428 (open) draft-mtp "roughly halves prompt processing on multi-GPU layer split (single GPU is fine)"; #28484 (closed) draft-MTP over RPC 25-30% slower, acceptance unchanged.
- Real MTP + tensor-split config (V100, #31127): `--split-mode tensor --tensor-split 1,1 ... --spec-type draft-mtp --spec-draft-n-max 3 --spec-draft-ubatch 256 --spec-draft-sampling greedy`, build `-DGGML_CUDA_NCCL=ON`.
- Related: #29928 (merged 2026-10-07) GLM5Next MTP (another GDN-hybrid MoE); speculative.md ngram-mod: "MoEs require long drafts."

## 4. Gated DeltaNet (GDN) CUDA on older GPUs

- Two CUDA kernels (ggml/src/ggml-cuda/): `gated_delta_net.cu` = base scalar kernel (f32 FMA loop, warp reduction, S_v in {16,32,64,128} else GGML_ABORT; no arch-conditional code — runs on any CC, incl. sm_50/sm_60). `gated-delta-net-mma.cu` = fast chunked kernel: 128x128 state, split-BF16 hi/lo mma tiles, chunk of C tokens; from #29353 (merged 2026-10-14, "upstreaming a kernel developed in downstream [QVAC fabric]... Credits also to @lukdmine").
- The gate (verbatim, `select_gdn_mma_path`): "Enable only architectures benchmarked for this schedule. MMA support alone does not imply a speedup." NVIDIA side: MMA path only when cc is GA10X, ADA_LOVELACE, BLACKWELL or DGX_SPARK, else `return gdn_path::ar` (falls back to the base scalar kernel). Eligibility also: H_k == 16, H in {16,32,48,64}, n_tokens >= 64, S_v == 128, q ne[0] == 128. -> **Pascal (sm_60/61), Maxwell (sm_50), and even Volta/Turing run the base scalar kernel**; there is no wmma/dp4a GDN code for sm_50/60. No pre-Volta-specific "slow path" exists beyond the absence of the tensor-core kernel.
- MMA kernel perf (#29353): Qwen3.5-35B-A3B PP +10.8%..+20.6% (PRO 6000 Q8_0 pp2048 13,653.58 -> 16,459.56; 5090 Q4_K_S 12,477.32 -> 14,524.81; 4090 Q4_K_S 10,872.34 -> 12,044.25; 3090 +6.9%); dense 27B +3.1%..+6.4% (4090 Q4_K_M 3,336.69 -> 3,438.65). Correctness: KL 0.000463 +/- 0.000029; top-token agreement 98.824%.
- Ports: #30207 (draft, Vulkan): "Vulkan port of the CUDA chunked kernel in #29353 to NV_coopmat2 and KHR_coopmat_maintenance1"; #31762 (draft 2026-11-05, SYCL ESIMD): GATED_DELTA_NET op speedups up to x2.96 at 1024 seq tokens (Arc A770), model +4.3% pp512 Qwen3.8-27B.
- m10dis: GDN layers never run on GM107 — "GDN and attention layers, QSA indexer, router, norms | RTX 3070 Ti | vLLM 0.32, CUDA graphs; GDN, QSA and hyper-connection weights in FP8" (ARCHITECTURE.md); the model is "48: 36 linear-attention (Gated DeltaNet), 12 full attention".
- Legacy-GPU context: #30727 (open) "CUDA: improve cuBLAS compatibility with Legacy GPUs" — pre-Volta cuBLAS algorithm select, FP32 fallback, "enable cuda graphs on older gpus... ballpark 25% on my k40c gpus" (K40 CC 3.5, CUDA 11.8), references #25680.
